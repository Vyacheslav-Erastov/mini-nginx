# Mini-Nginx на asyncio, потоках и selectors

reverse proxy для HTTP/1.1 с тремя реализациями сетевого слоя:
на `asyncio`, на блокирующих сокетах с пулом потоков и на неблокирующих
сокетах со стандартным модулем `selectors`.

## Текущее состояние

Уже реализовано:

- приём TCP-соединений;
- минимальный парсинг стартовой строки и заголовков HTTP-запроса;
- потоковая передача тела запроса без полной загрузки в память;
- потоковая передача ответа upstream клиенту;
- backpressure через `await writer.drain()` в asyncio-реализации и блокирующий
  `socket.sendall()` в реализации на потоках;
- backpressure через ограниченные буферы и управление `EVENT_READ` в
  реализации на selectors;
- round-robin между несколькими upstream;
- лимит клиентских соединений и соединений к каждому upstream;
- connect/read/write таймауты;
- общий таймаут запроса в asyncio-реализации и реализации на selectors;
- YAML-конфигурация;
- клиентский HTTP keep-alive;
- переиспользование TCP-соединений к upstream;
- парсинг заголовков ответа и логирование HTTP-статуса;
- структурированные логи через `structlog`;
- минимальные счётчики и таймеры;
- нагрузочное тестирование через k6.

Asyncio-реализация обслуживает соединения корутинами в одном event loop.
Реализация на потоках назначает клиентское соединение потоку из
`ThreadPoolExecutor` и дополнительно умеет запускать несколько процессов.
Реализация на selectors обслуживает все клиентские и upstream-сокеты одним
event loop без корутин и отдельного потока на каждое соединение.

Во всех реализациях upstream выбирается по round-robin, а исправное keep-alive
соединение возвращается в пул после обработки запроса. Asyncio и потоки
ограничивают занятые соединения семафорами. Реализация на selectors хранит
счётчики открытых соединений в event loop, поэтому locks и semaphores ей не
нужны.

## Как проходит запрос

1. `ProxyServer` принимает TCP-соединение клиента.
2. Клиент занимает место в `max_client_conns`.
3. `HttpRequestHead` читает стартовую строку и заголовки до пустой строки.
4. `UpstreamPool` выбирает upstream по round-robin и резервирует место в его
   лимите соединений.
5. Proxy переиспользует свободное соединение либо открывает новое
   TCP-соединение к выбранному upstream.
6. Заголовки и тело запроса отправляются upstream.
7. Ответ сразу передаётся клиенту кусками по мере получения.
8. Если upstream разрешил keep-alive, соединение возвращается в пул для
   следующего запроса.
9. Клиентское соединение остаётся открытым для следующего запроса либо
   закрывается.

В asyncio-реализации, пока корутина ожидает данные сокета, event loop может
обслуживать другие соединения в том же потоке. `writer.drain()` ограничивает
рост буфера, если получатель читает медленнее отправителя.

В реализации на потоках `accept()` передаёт каждое клиентское соединение в
`ThreadPoolExecutor`. Блокирующие `recv`/`read` и `sendall` освобождают GIL на
время сетевого I/O, поэтому другие потоки продолжают обслуживать свои
соединения. `BoundedSemaphore` ограничивает число клиентов и соединений к
upstream, а `Lock` защищает round-robin и списки свободных соединений.

В реализации на selectors все сокеты работают в неблокирующем режиме и
регистрируются в `selectors.DefaultSelector`. Для каждого клиента создаётся
stateful handler, который переходит между чтением запроса, подключением и
записью в upstream, чтением ответа и его отправкой клиенту. `connect_ex()`
запускает неблокирующее подключение, а события `EVENT_READ` и `EVENT_WRITE`
показывают, когда операцию можно продолжить.

Выходные буферы ограничены 64 КиБ. Когда буфер заполняется, handler временно
отключает чтение из socket-источника и включает его снова после отправки
накопленных данных. Таймауты хранятся как абсолютные deadlines на основе
`monotonic()`, а ближайший deadline передаётся в `selector.select(timeout)`.
Клиентский keep-alive и уже полученные pipelined-запросы обрабатываются
последовательно.

## Конфигурация

Пример [proxy/config.yml](./proxy/config.yml):

```yaml
listen: "127.0.0.1:8090"
upstreams:
  - host: "127.0.0.1"
    port: 9002
  - host: "127.0.0.1"
    port: 9003
timeouts:
  connect_ms: 1000
  read_ms: 15000
  write_ms: 15000
  total_ms: 30000
limits:
  max_client_conns: 1000
  max_conns_per_upstream: 100
```

Таймауты задаются в миллисекундах, а `TimeoutPolicy` переводит их в секунды.
Asyncio-реализация передаёт их в `asyncio.wait_for`, реализация на потоках —
в методы блокирующих сокетов, а реализация на selectors вычисляет по ним
deadlines для event loop.

Реализация на потоках читает
[proxy_threads/config.yml](./proxy_threads/config.yml). Формат совпадает, но
дополнительно можно задать число worker-процессов:

```yaml
workers: 1
```

Каждый worker создаёт собственный TCP-сервер с `SO_REUSEPORT`, пул потоков и
пул соединений к upstream.

Реализация на selectors читает
[proxy_selectors/config.yml](./proxy_selectors/config.yml). Формат
конфигурации совпадает с остальными реализациями. Поле `workers` пока не
используется: запускается один selector event loop в одном процессе.

Подробное описание конечного автомата, backpressure, upstream pool и deadlines
находится в [proxy_selectors/README.md](./proxy_selectors/README.md).

## Локальный запуск

Установить зависимости:

```bash
uv sync
```

Запустить первый upstream:

```bash
INSTANCE_ID=upstream-1 uv run uvicorn tests.echo_app:app \
  --host 127.0.0.1 --port 9002
```

Во втором терминале запустить второй upstream:

```bash
INSTANCE_ID=upstream-2 uv run uvicorn tests.echo_app:app \
  --host 127.0.0.1 --port 9003
```

В третьем терминале запустить asyncio-реализацию:

```bash
uv run -m proxy.main
```

Или запустить реализацию на потоках:

```bash
uv run -m proxy_threads.main
```

Или запустить реализацию на selectors:

```bash
uv run -m proxy_selectors.main
```

Все три реализации слушают один адрес, поэтому одновременно их запускать
нельзя.

Проверить GET и POST:

```bash
curl -v http://127.0.0.1:8090/
curl -v -X POST http://127.0.0.1:8090/echo -d 'hello world'
```

При последовательных запросах ответы должны по очереди содержать
`upstream-1` и `upstream-2`.

основную часть этого значения составляет зарезервированное адресное
пространство под стеки потоков.

## Границы минимальной HTTP-поддержки

Проект сознательно не реализует всю спецификацию HTTP/1.1. На этапе MVP:

- тело запроса определяется по `Content-Length`;
- chunked request body не поддерживается;
- HTTPS/TLS не поддерживается;
- upgrade до WebSocket не поддерживается;
- health-check, retry и circuit breaker оставлены на следующие этапы;
- полноценная очистка всех hop-by-hop заголовков пока не реализована.

Эти ограничения следует учитывать при интерпретации нагрузочных тестов.
