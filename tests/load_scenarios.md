# Нагрузочные сценарии

Все профили находятся в одном файле `tests/load_test.js`. Нужный профиль
выбирается переменной `TEST_TYPE`, поэтому проверки ответов и подсчёт запросов
по upstream не дублируются.

## Подготовка

Перед тестированием должны работать два upstream и proxy:

```bash
INSTANCE_ID=upstream-1 uv run uvicorn tests.echo_app:app \
  --host 127.0.0.1 --port 9002

INSTANCE_ID=upstream-2 uv run uvicorn tests.echo_app:app \
  --host 127.0.0.1 --port 9003

uv run -m proxy.main
```

Быстрая ручная проверка:

```bash
curl -v http://127.0.0.1:8090/
curl -v -X POST http://127.0.0.1:8090/echo -d 'hello world'
```

По умолчанию `run_k6.sh` обращается к `http://127.0.0.1:8090`. Другой адрес
можно передать через `BASE_URL`:

```bash
BASE_URL=http://127.0.0.1:8080 TEST_TYPE=smoke ./run_k6.sh
```

## Рекомендуемый порядок

1. `smoke` - проверить функциональную корректность.
2. `keepalive` - проверить повторное использование клиентского соединения.
3. `load` - получить рабочий baseline.
4. `stress` - найти начало деградации.
5. `timeout` - проверить зависший upstream.


## Smoke

```bash
TEST_TYPE=smoke ./run_k6.sh
```

Один VU выполняет 10 запросов. Сценарий проверяет:

- статус `200`;
- ответ действительно пришёл от одного из upstream;
- GET и POST проходят через proxy;
- round-robin распределяет запросы между двумя инстансами.

Ожидается `0%` ошибок и примерно равное количество запросов к upstream.

## Load

```bash
TEST_TYPE=load ./run_k6.sh
```

Количество VU плавно растёт от 5 до 50, затем опускается до нуля. Это основной
сценарий для сравнения изменений в коде.

Пороговые значения:

- доля ошибок меньше `1%`;
- `p(95)` меньше `500 ms`;
- `p(99)` меньше `1000 ms`.

Результат этого теста стоит сохранить как baseline: RPS, среднее время,
`p(95)`, `p(99)`, максимальное время и объём переданных данных.

## Stress

```bash
TEST_TYPE=stress ./run_k6.sh
```

Нагрузка повышается до 200 VU. Цель - не получить красивое число RPS, а найти
момент, когда начинают расти latency, ошибки и таймауты.

Ослабленные пороги stress-профиля:

- доля ошибок меньше `5%`;
- `p(95)` меньше `1500 ms`.


## Keep-alive

```bash
TEST_TYPE=keepalive ./run_k6.sh
```

Каждая итерация отправляет три последовательных запроса. k6 по умолчанию
пытается переиспользовать HTTP-соединение. Для второго и третьего запроса
проверяется, что время установки TCP-соединения равно нулю.

Метрика `connection_reused` должна быть больше `90%`. До реализации клиентского
keep-alive этот порог ожидаемо не пройдёт. После реализации тест подтверждает,
что proxy не просто возвращает заголовок `Connection: keep-alive`, а реально
обрабатывает несколько запросов в одном TCP-соединении.

## Timeout

```bash
TEST_TYPE=timeout ./run_k6.sh
```

Тест вызывает `/delay/20`. При текущем `read_ms: 15000` upstream отвечает
дольше разрешённого времени, поэтому proxy обязан завершить ожидание примерно
через 15 секунд.

Переменная `DELAY_SECONDS` позволяет изменить задержку:

```bash
DELAY_SECONDS=35 TEST_TYPE=timeout ./run_k6.sh
```

Метрика `timeouts_observed` должна быть больше нуля.

## Интерпретация результатов k6

- `http_reqs` - выполненные запросы и средний RPS;
- `http_req_duration` - полное время HTTP-запроса;
- `avg` - среднее, которое может скрывать редкие медленные запросы;
- `p(95)` - 95% запросов были быстрее этого значения;
- `p(99)` - показывает поведение медленного хвоста;
- `http_req_failed` - доля сетевых и HTTP-ошибок;
- `iteration_duration` - время всей функции сценария;
- `vus`/`vus_max` - текущее и максимальное количество виртуальных клиентов;
- `upstream_1_requests` и `upstream_2_requests` - проверка round-robin;
- `connection_reused` - доля повторно использованных клиентских TCP-соединений;
- `timeouts_observed` - число предсказуемо завершённых медленных запросов.

При двух исправных upstream разница их счётчиков обычно не превышает одного
запроса. Большая разница означает ошибку балансировки или ошибки одного из
инстансов.
